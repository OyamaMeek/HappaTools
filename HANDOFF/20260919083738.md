## 任务目标

用户要求“根据 `Claude/Claude.md` 在 main 分支完成开发”。产品是一个 macOS 11+ 原生 Swift 应用 HappaTools：

- 在 Finder 中提供 Git 操作入口，暂存当前仓库全部更改、提交多行说明并推送当前分支配置的 upstream。
- 在 Finder 中提供创建空白 `README.md` 的入口，已有文件、目录和符号链接都不能被覆盖。
- 主应用提供设置、扩展状态提示、操作历史、日志筛选和日志清理。
- 使用 App Group 共享设置和 SQLite 日志。

实现要点：

- Git 使用 `Process` 和参数数组执行，不拼接 shell 命令。
- 每条命令 30 秒超时，stdout/stderr 各自最多保留 1 MiB；超时会终止进程组，避免 hooks 孤儿进程。
- 先验证当前目录是 Git 仓库、当前分支可识别、当前分支有 upstream，再执行 `git add -A`，避免无 upstream 时产生副作用。
- 推送使用实际 upstream remote 和完整的 `refs/heads/...` 目标，避免同名 tag 导致错误推送。
- 保留本地提交：commit 成功但 push 失败时不会 reset。
- 每个仓库使用跨进程锁，拒绝同仓库并发操作。
- 仓库根路径只移除命令输出最后一个换行，保留路径末尾空格等真实字符。
- README 使用原子创建，拒绝覆盖已有文件，也不跟随符号链接。
- SQLite 使用原生 `SQLite3` C API、参数绑定、WAL、事务和 30 天清理；查询默认最多 100 条。
- `FinderRequest` 严格校验自定义 URL：只允许 `happatools` scheme、`git`/`readme` host、一个 `path` query、绝对路径，不接受凭据、端口、fragment、相对路径或 NUL。

### 当前最终的沙盒架构

最初尝试让扩展直接执行 Git，但 macOS 的 `pkd` 明确拒绝未沙盒化的 Finder Sync extension，日志原文是 `plug-ins must be sandboxed`。当前架构是：

```text
Finder
  ├─ HappaTools Git FinderSync.appex（sandbox=true）
  └─ HappaTools README FinderSync.appex（sandbox=true，放在独立 helper app）
        ↓ happatools://git?path=... / happatools://readme?path=...
HappaTools.app（sandbox=false）
        ↓ 用户确认后
后台 GitWorkflow / ReadmeCreator
```

- 主应用 `HappaTools.app` 是非沙盒，负责访问仓库、执行 Git、创建 README 和保存日志。
- Git 扩展仍直接嵌在主应用：`HappaTools.app/Contents/PlugIns/FinderSyncExtension.appex`。
- README 扩展放入独立的 `Contents/Helpers/HappaTools README.app`，路径为：
  `HappaTools.app/Contents/Helpers/HappaTools README.app/Contents/PlugIns/ReadmeFinderSyncExtension.appex`。
- `ReadmeExtensionHost/main.swift` 只是启动后立即退出的轻量宿主，不运行 `AppModel`，不注册 URL scheme，也不清理共享 busy 状态。
- README extension 计算 containing app 路径时，需要从 helper 再上移三层到外层 HappaTools.app；Git extension 只需上移三层。
- helper 自己嵌入 `HappaToolsShared.framework`，README extension 的 runpath 指向 helper 内部的 `Contents/Frameworks`。
- `scripts/build.sh` 现在按 framework → extension → helper → main app 的顺序签名；不要把 README extension 当成主应用的直接 child 再签一次。

这个 helper 结构是为当前这台 macOS 15.7.7 的实际系统设置行为增加的兼容层。当前系统会把同一 containing app 内的两个 Finder Sync extension 在摘要中显示为 HappaTools，但打开“文件提供程序”详情时完全省略 HappaTools 开关。临时注销 README extension 后，详情立即出现单个 HappaTools 开关；把 README extension 放到独立 helper app 后，详情显示两个独立开关。

## 绝对不要踩的坑

- 不要执行 `git add .`。仓库里有用户原始的 `AGENT.md`、`Claude/Claude.md`，以及开发临时文件；必须明确列出要暂存的路径。
- 不要提交 `.env`、API key、证书、provisioning profile、`.log`、`.build`、`.agent` 或安装备份。
- 不要把 Finder Sync extension 改回 `app-sandbox=false`。`pkd` 会拒绝加载，系统日志是 `plug-ins must be sandboxed`。
- 不要把两个 Finder Sync extension 继续放在同一个 containing app 并期待 macOS 15.7.7 的详情页列出两个开关；当前实机 A/B 已证明会出现摘要有名称、详情没有开关的状态。保留独立 `Contents/Helpers/HappaTools README.app`。
- 不要让 helper 启动完整 `AppModel`。它只为让系统发现 README extension，启动后立即退出；复用主应用会清除 `operationInProgress`、打开数据库并造成错误状态。
- 不要在 helper 注册 `happatools` URL scheme。scheme 只属于外层 HappaTools.app，扩展的请求最终必须到非沙盒主应用。
- README extension 查找主应用时不要只上移三层；它位于 helper 内，需先得到 helper，再额外上移三层到外层 HappaTools.app。Git extension 才是普通上移三层。
- 不要漏嵌入 helper 自己的 `HappaToolsShared.framework`，也不要使用错误的 `@executable_path` runpath。
- 不要先签主应用再签里面的内容。临时签名顺序必须是 framework → extension → helper → outer app；正式 Developer ID 也要保持 inside-out。
- 不要把 `FIFinderSyncController.isExtensionEnabled` 当成两个扩展都已启用的证明；它不能替代 README 的独立 UI 验证。
- 不要尝试在 Finder extension 菜单里塞自定义 `NSTextView`。Finder 跨进程菜单只可靠传递标准 `NSMenuItem`；当前做法是 extension 发 URL，主应用弹多行提交框。
- 不要把 `targetedURL()` 为 nil 时猜成 home 或当前目录。必须要求用户选择文件夹；虚拟目录、云盘和第三方 Finder 扩展都可能返回 nil。
- 不要把主应用普通 home 文件可读误报成 Full Disk Access。当前只探测 Mail 目录，结果未知或拒绝时要如实显示；FDA 必须由用户在系统设置手动授权。
- 不要在 Git workflow 中硬编码 `origin` 或默认分支。使用当前检出的分支及 upstream；默认分支设置只用于空配置展示。
- 不要删掉 push 失败后的本地 commit，也不要为“修复”使用 force push 或 reset。
- 不要把当前已安装的 ad hoc 构建称为可公开发布版本。Developer ID、Hardened Runtime、公证和 Gatekeeper 仍未完成。
- 使用系统设置或 Finder 做端到端验证时，遵守 CUA 规则：每次 UI 操作后重新读取 accessibility state；不要用 AppleScript/JXA/CGEvent 替代 CUA。
